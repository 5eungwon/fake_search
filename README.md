# 집온 — 원거리 주택 외부 점검 PMF 랜딩페이지

기존 FitView 페이지를 집온으로 교체했습니다. Next.js 16 / React 19 기반이며, 신청 모달과 저장 API, 보호된 실험 요약·CSV 내보내기를 포함합니다.

## 실행

```sh
npm install
cp .env.example .env.local
npm run dev
```

http://localhost:3000 에서 확인합니다. 개발에서는 신청과 이벤트가 `.data/experiment.json`에 저장됩니다. 실제 연락처는 Git에 포함되지 않습니다.

## Upstash 연결

`.env.local` 파일에 Upstash Console의 해당 Redis DB에 표시된 `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`을 입력합니다. 토큰은 쓰기 권한이 있는 REST 토큰이어야 합니다. 이 파일은 Git에서 제외됩니다.

```sh
npm run check:redis
```

이 명령은 고유한 테스트 키에 쓰기·읽기·삭제를 수행하고, URL이나 토큰을 출력하지 않습니다. 성공 후 개발 서버를 재시작하세요. 배포 시에는 동일한 값을 호스팅 서버의 환경변수에도 등록해야 합니다.

## 실제 모집 전 설정

- `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`: Upstash Redis의 REST 연결 정보. 프로덕션에서 신청과 이벤트를 영구 저장하는 데 필요합니다. 레코드 TTL은 90일입니다.
- `PMF_ADMIN_TOKEN`: 임의의 긴 비밀 값. 운영자 통계와 신청 CSV를 보호합니다. 브라우저 코드에 노출하지 마세요.
- 위 저장소가 연결되지 않은 프로덕션에서는 API가 503을 반환하며 접수 완료로 표시하지 않습니다.
- 단일 프로세스 서버에 영구 볼륨이 있을 때만 `PMF_DATA_DIR`로 파일 저장을 명시할 수 있습니다. 서버리스 / 여러 인스턴스에는 Redis를 사용하세요. 파일 저장은 요청 시 90일 지난 레코드를 정리하므로, 실제 운영에는 Redis TTL을 권장합니다.
- 개인정보 수집 안내의 운영 주체와 실제 문의 창구를 운영팀 정보로 확정한 뒤 공개하세요. 현재는 시범 운영 연락에 회신해 철회를 요청하도록 안내합니다.
- 주택의 정확한 주소·부재 일정·열쇠 정보는 수집하지 않습니다.

기존 Next.js 호스팅(Vercel 등)에 배포 가능한 소스입니다. 이번 작업에서는 공개 배포나 결제 연동을 하지 않았습니다.

## 페이지와 신청 흐름

주택 관리 경험 설문 → 응답 저장 → 서비스·요금 안내 → 선택적 연락처 신청 → 첫 이용 쿠폰 자동 발급.

- 현재 서비스 개발 중이며, 월 1회 외부 점검의 출시 예정 요금은 9,900원입니다. 사전 신청만으로 결제하거나 방문이 확정되지 않습니다.
- 설문은 Q1 별도 관리 주택, Q2 관리 방법(복수 선택·기타·거의 관리하지 않음 포함), Q3 실제 관리 지연 경험, Q4 가장 큰 이유로 구성합니다. 주택이 없거나 미룬 경험이 없으면 관련 질문을 건너뜁니다.
- 설문은 연락처 없이 별도로 저장합니다. 저장된 설문과 신청을 연결하므로 서비스에 신청하지 않은 사람도 분석에 포함합니다.
- 신청은 시·군과 연락처, 월 9,900원 유료 이용 의향, 개인정보 동의를 받습니다. 인터뷰 연락 동의는 선택입니다. 기존 주택 유형·마지막 방문 등 추가 질문은 제거했습니다.
- 첫 이용 1,000원 할인 쿠폰은 신청 저장 후 자동 발급합니다. 기본 요금 기준 첫 결제 8,900원, 이후 월 9,900원입니다. 접수일부터 90일, 첫 결제 1회, 다른 할인 중복 불가, 점검 가능 지역에서 적용합니다.
- 쿠폰 발급만 실패하면 신청은 보존하고 발급 재시도 버튼을 표시합니다. 같은 접수의 재시도는 동일 쿠폰을 반환합니다. 결제 연동은 아직 없으므로 운영팀이 실제 결제 때 코드와 사용 이력을 확인합니다.
- 요금과 쿠폰 설정은 lib/offer.ts, 설문 선택지와 핵심 타깃 가설은 lib/survey.ts에서 관리합니다. 신청에 제시한 요금·버전과 연결된 설문 ID를 저장합니다.
- 샘플 리포트와 주택 이미지는 실제 고객 점검 증거가 아닙니다.

## 실험 지표

`POST /api/track`: `landing_view`, `apply_click`, `report_view`, `form_start`, `form_step_complete`를 기록합니다. 신청 완료 수는 실제 저장된 신청 레코드에서 계산합니다.

유입 URL 예시:

```text
/?utm_source=naver_cafe&utm_campaign=pilot_01&utm_content=distance
/?utm_source=naver_cafe&utm_campaign=pilot_01&utm_content=favor
```

`utm_content`는 모집글 메시지를 구분하는 값입니다. 페이지 문구 자체를 바꾸는 A/B 기능은 아닙니다. 같은 대상·비슷한 노출 조건에서 비교하세요.

`GET /api/experiment`에 `Authorization: Bearer <PMF_ADMIN_TOKEN>` 헤더를 보내면 이벤트 횟수, 저장된 신청 수, 유입 경로별 신청·실제 관리 주택 보유 여부·유료 이용 의향·요금 확인을 마친 유료 예약(`paidReservations`)·실제 쿠폰 발급(`couponsIssued`)을 확인합니다. `?format=csv`로 신청 레코드를 내려받을 수 있습니다. 인증 없는 요청은 401을 반환합니다. 통계 응답에 연락처나 쿠폰 코드를 포함하지 않으며 CSV에만 포함합니다. CSV에는 `offeredPrice`, `offerVersion`, `priceConfirmed`, `couponCode`, `couponDiscount`, `couponIssuedAt`, `couponExpiresAt`도 포함합니다.

이벤트는 **발생 횟수**이며 고유 방문자/고유 신청자 전환율이 아닙니다. 새로고침이나 반복 클릭도 집계됩니다. 같은 접수 ID의 재시도는 한 건으로 저장하지만, 새 접수 ID로 다시 신청한 동일 연락처는 별도 레코드이므로 모집 분석 시 확인하세요. 유료 예약과 쿠폰 발급을 별도로 집계합니다. 둘 다 실제 결제는 아니므로, 이후 쿠폰 적용 첫 결제와 할인 없는 재결제를 별도로 기록해야 합니다. 랜딩페이지에서 확인할 수 있는 것은 참여 의향과 가격 반응이며, PMF나 실제 구매의 증거는 아닙니다.

## 다음 검증

1. 2주 동안 실제 관리 중인 주택의 소유자·관리자 5명 이상 모집을 초기 실험 목표로 둡니다. PMF 통과 기준이 아닙니다.
2. 최근 방문 목적이 `집의 외부 상태 확인`인 신청자를 우선 인터뷰하고, 외부 리포트가 어떤 방문을 대신하는지 확인합니다.
3. 한 지역에서 범위를 합의하고 실제 결제 → 점검 완료를 기록합니다. 랜딩페이지 신청 수와 분리합니다.
4. 점검 전 방문 계획과 결과 이후의 실제 방문 여부를 기록하고, 다음 점검 **재결제**를 확인합니다.
5. 지역 주민의 이동·작업 시간, 보수 만족과 플랫폼 검수·응대 비용도 함께 기록합니다.

## 관리 경험 설문 흐름

메인 화면의 `설문조사 참여하기` 버튼을 누르면 별도 `/survey` 페이지로 이동합니다. 이 페이지에서 최대 4개 질문에 답하고 `POST /api/surveys`로 응답을 저장합니다. 별도 주택이 없으면 Q1만 제출하고, 미룬 경험이 없으면 Q4를 건너뜁니다. Q2는 복수 선택이며 `거의 관리하지 않음`은 단독 선택합니다. Q2·Q4의 기타에는 자유 입력란이 열립니다. 설문은 연락처 없이 제출할 수 있습니다.

설문 완료 후 주택 보유 응답자에게 월 9,900원 서비스와 첫 이용 1,000원 할인 쿠폰을 안내합니다. 신청 버튼 → 시·군과 연락처 → 유료 이용 의향 및 개인정보 동의 → 신청 저장·쿠폰 자동 발급으로 이어집니다. 서버는 저장된 설문의 ID와 요청 ID를 확인하고 신청에 연결하며, 기존 주택 유형·마지막 방문 등 중복 질문은 제거했습니다.

`GET /api/experiment`의 `funnel`에서 설문 제출 수, 별도 주택 보유 응답, 관리 지연 경험, 핵심 타깃, 연결된 신청 수와 핵심 타깃 신청률을 확인합니다. 핵심 타깃의 실험 정의는 `별도 주택 있음 + 실제 관리 지연 경험 + 시간/거리/번거로움/지인 부탁 부담`입니다. 비용·낮은 우선순위·기타 응답도 보존하지만 이 정의의 핵심 타깃에는 포함하지 않습니다. 이는 분석용 가설이며 PMF 판정 기준이 아닙니다. 같은 설문의 반복 신청은 전환 계산에서 한 건으로 처리합니다. 고유 개인 식별은 하지 않으므로 같은 사람이 새 설문을 제출하면 별도 응답입니다.

설문 CSV: `GET /api/experiment?format=csv&dataset=surveys`. 신청 CSV에는 연결된 설문 응답도 함께 포함합니다. 두 내보내기 모두 기존 운영자 Bearer 토큰이 필요합니다. 기존 신청 기록도 보존하며, 설문 연결이 없는 과거 신청은 새 설문 전환율에 포함하지 않습니다.

설문은 메인 화면에 표시되지 않습니다. 메인의 헤더·첫 화면·요금·하단·모바일 버튼이 모두 `/survey`로 이동하며 UTM 유입 정보를 유지합니다. `/survey`에서는 설문 제출 후 서비스 신청·쿠폰 발급을 계속 진행할 수 있고 `메인으로 돌아가기` 링크를 제공합니다. `survey_entry_click`은 메인 버튼 클릭, `survey_view`는 설문 페이지 방문 횟수입니다.

Q3는 가장 최근의 관리 지연 기간을 선택하는 질문입니다. 미룬 적 없음 / 1주 미만 / 1주 이상~1개월 미만 / 1개월 이상~3개월 미만 / 3개월 이상~6개월 미만 / 6개월 이상 / 직접 입력 / 잘 기억나지 않음으로 구성하며, 직접 입력 시 기간을 적는 칸을 제공합니다. 방문 간격이 아니라 원래 관리하려던 시점에서 늦어진 기간을 묻습니다. 기간 응답에서 delayed를 서버가 계산합니다. 미룬 적 없음은 false, 기억나지 않음은 null로 저장하고 Q4를 건너뜁니다. delayDuration과 delayDurationOther는 Redis·CSV에 저장되며 운영자 funnel.delayDurations에 기간별 분포를 제공합니다. 과거 응답에는 기간을 추정해 넣지 않습니다.
